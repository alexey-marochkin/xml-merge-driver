# XML Merge для Windows

## Согласованные требования

- Реализация на Go. Первая версия предназначена для Windows и Git for Windows.
- Основной корпус проверки — объемные XML конфигуратора 1С. Иные XML поддерживаются в рамках реализованных XML-возможностей.
- Для base, local, remote строятся DOM. Идентификация не зависит от позиции элемента.
- Один профиль на пару namespace URI + локальное имя root. Дополнительного выбора по пути файла или версии нет.
- Способы идентификации: атрибут; набор дочерних элементов, образующий составной ключ; непосредственное текстовое значение без текста потомков.
- Собственная настройка переопределяет наследуемую. При отсутствии собственной настройки используется ближайший предок с явно заданной настройкой, включая транзитивное наследование. Настройки предков не копируются и не изменяются.
- Настройка узла определяет также значимость порядка его детей.
- До сравнения выполняется отдельная подготовка: загрузка правил, проверка покрытия и применимости с учетом наследования, автоматическое создание однозначных правил. Пока покрытия недостаточно, сравнение изменений не запускается и несопоставленные деревья сравнения не показываются. Открывается только редактор недостающих/неприменимых правил с необходимыми примерами структуры и значений. После сохранения подготовка повторяется.
- Автоматическое правило проверяется на каждом применении. Дубликаты и отсутствующие компоненты ключа не дают соответствия.
- Перемещения и изменения ключей входят в целевую первую версию. Если ключ изменен и иных однозначных признаков нет, возникает конфликт соответствия. Для перемещений между родителями требуется область поиска и проверка глобальной уникальности.
- Порядок атрибутов, кодировка и порядок узлов сохраняются. Переводы строк XML, текста и CDATA сохраняются раздельно, без глобальной нормализации.
- При незначимом порядке основой служит последовательность local. Новые remote-узлы вставляются относительно сопоставленных соседей, при их отсутствии — в конец. Новые атрибуты добавляются в конец.
- Результат сохраняется в кодировке local. Непредставимый символ вызывает ошибку/конфликт, без автоматической смены кодировки и подстановки числовых ссылок.
- База правил общая для пользователя Windows, формат XML, путь по умолчанию `%LOCALAPPDATA%\XmlMerge\rules.xml`. Для командного проекта поддерживается версионируемый XML-файл правил в репозитории, имеющий приоритет над личной базой; личное переопределение командного правила возможно только явно. Новые локальные правила включаются в командную базу обычным коммитом. Сам файл правил исключается из обработки нашим merge driver.
- CLI merge driver при успехе записывает результат в local (%A), при любом конфликте оставляет этот файл побайтно неизменным и возвращает Git ненулевой статус.
- Git merge tool через CLI запускает отдельное интерактивное приложение в текущей пользовательской сессии Windows. Приложение содержит локальный веб-сервер на собственном свободном порту и собственное окно с веб-интерфейсом. После подготовки правил показывает три сопоставленных DOM, подсветку конфликтов и выбор изменений. Только явное сохранение полностью разрешенного результата изменяет файл MERGED; отмена ничего не записывает.
- Ручной режим позволяет открыть произвольные три XML без Git.

## Архитектура

1. `internal/xmltree`: DOM с исходными фрагментами и информацией о кодировке. Семантические значения отделены от лексического представления. Неизмененный документ восстанавливается побайтно.
2. `internal/rules`: XML-профили, поиск и наследование правил, извлечение ключей, проверка и сохранение общей базы.
3. `internal/merge`: сопоставление трех деревьев, изменения относительно base, конфликты и построение результата.
4. `cmd/xmlmerge`: самостоятельный CLI для Git и CI/CD, а также запуск интерактивного приложения по явному запросу или в режиме Git merge tool.
5. `cmd/xmlmerge-ui`: отдельный EXE, собственное окно на WebView2 и локальный HTTP-сервер. Использует общее Go-ядро непосредственно. Редактор правил — первый экран при недостатке настроек; три сопоставленных DOM доступны после успешной подготовки при ручном сравнении/разрешении конфликтов.
6. `internal/prepare`, `internal/interactive`, `internal/ui`: проверка достаточности правил, состояние операции, HTTP API и встроенные HTML/CSS/JS-ресурсы.

Входные DOM не изменяются при вычислении результата. Результат сначала строится и проверяется в памяти. Запись выполняется только при полном успехе. Источником байтов неизмененных участков остается local; принятые фрагменты remote сохраняют собственные переводы строк и транскодируются только в кодировку результата, если необходимо.

## Интерактивное приложение и терминальный сервер

- Распространяются два приложения: `xmlmerge.exe` и `xmlmerge-ui.exe`. XML-движок и правила находятся в общей Go-библиотеке, используемой обоими приложениями.
- Один интерактивный запуск соответствует одной операции и одному окну в текущей сессии Windows. Одновременные операции одного пользователя также получают отдельные экземпляры. Служба на весь терминальный сервер не требуется.
- Приложение сразу привязывает listener к `127.0.0.1:0` и использует назначенный Windows порт. Предварительное сканирование свободных портов не применяется.
- HTTP-сервер принадлежит процессу окна. Закрытие окна отменяет незавершенную работу, прекращает обработку запросов, закрывает listener и завершает процесс. Приложение не остается в трее или в фоне. При аварийном завершении процесса сокет освобождает ОС.
- Доступ к операции проверяется секретом отдельного запуска; один лишь localhost/номер порта не является изоляцией пользователей терминального сервера. Секрет не записывается в обычные журналы. Личные временные файлы и данные WebView разделяются по пользователю и операции.
- CLI ожидает интерактивный процесс и сообщает результат вызывающему Git. Успех означает проверенный и явно сохраненный результат; закрытие окна до сохранения, ошибка или отсутствие UI дают ненулевой статус. Файл результата при отмене не изменяется.
- Подготовленный результат передается через отдельный временный файл с проверкой перед атомарной записью в назначенный путь. Сохранение правила — самостоятельное явное действие; оно не означает сохранения результата слияния.
- Для запуска из CLI предусматривается явный интерактивный режим. Обычный merge driver и запуск в CI/CD остаются без интерфейса: недостаток правил/конфликт возвращает диагностику и ненулевой статус.
- CLI и CI/CD могут получать путь базы правил явно. Во время одной операции используется фиксированный снимок настроек; после редактирования правил подготовка запускается заново с обновленным снимком. Параллельное изменение одного правила требует проверки версии перед сохранением.
- Собственное окно реализовано через `github.com/jchv/go-webview2`, без CGo. WebView2 Runtime является зависимостью интерактивного EXE, но не CLI. Требуется дополнительная проверка на целевом Windows Server/RDS; среда разработки не заменяет эту проверку.

Схема запуска: Git/пользователь → CLI → интерактивный EXE → подготовка правил → при необходимости редактор правил → сравнение → ручной интерфейс → сохранение либо отмена → статус CLI.

Отдельный запуск редактора: `xmlmerge-ui.exe --rules PATH` открывает базу без XML-документов. Без параметров используется `rules.xml` в каталоге исполняемого файла, независимо от рабочей папки; отсутствующий файл создается. Существующий некорректный или недоступный файл не заменяется пустым. Редактор позволяет создавать профили и редактировать правила без образцов; проверка уникальности ключей выполняется позже на конкретных документах. Закрытие этого режима возвращает 0. Автоматический выбор свободного порта и остановка при закрытии окна сохраняются.

Реализованный контракт: `xmlmerge-ui.exe merge|compare|rules --rules PATH [--user-rules PATH] --base PATH --local PATH --remote PATH [--output PATH]`. Для merge/compare output обязателен. CLI предлагает `compare`, `mergetool`, `ui` и `merge --interactive`; параметры передаются массивом аргументов без shell-интерпретации, пути приводятся к абсолютным. Порт не передается и выбирается приложением автоматически. UI: 0 — сохранено, 3 — отменено, 2 — ошибка. Автоматический CLI: 0 — успех, 1 — конфликт/недостаток правил, 2 — ошибка.

Текущий интерфейс позволяет подготовить правила, просмотреть сопоставленные деревья и сохранить бесконфликтное слияние; при конфликтах доступен явный выбор исходного документа целиком. Выбор отдельных изменений и ручное установление соответствий пока не реализованы.

## Семантика слияния

Основная область настройки уточнена: профиль root + имя элемента на любой глубине. Новые автоматические и ручные правила из сравнения проверяются на всех вхождениях этого расширенного имени. Полные пути сохранены для совместимости и точечных исключений. Импорт `.pmfmt` поддерживается форматом правил версии 2: селекторы имен, общая настройка `*`, явное сопоставление профиля с любым namespace при отсутствии URI в источнике, буквальные поля с префиксами, обрезка краевых пробелов в ключе и отдельный флаг отключения наследования у исходных шаблонов. Подробности ограничений переноса описаны в README.

- Одинаковые изменения принимаются один раз.
- Изменение только одной стороны принимается.
- Независимые изменения атрибутов и потомков объединяются.
- Разные изменения одного значения, удаление против редактирования, разные добавления с одним ключом и неоднозначные соответствия дают конфликт.
- Позиция не является запасным идентификатором повторяющихся элементов.
- Изменение ключа не должно молча трактоваться как удаление и добавление при наличии неоднозначности.
- Для значимого порядка применяется трехстороннее объединение последовательностей; противоречащие ограничения порядка дают конфликт.
- Для mixed content порядок текста и элементов сохраняется; эвристическая идентификация по объединенному тексту запрещена.
- Пользовательские правила имеют приоритет над автоматически выведенными.
- Неизвестные XML-возможности завершают операцию диагностикой до записи, а не теряются при сериализации.

## План реализации и критерии готовности

### 1. Основа XML и спецификация

DOM, namespaces, атрибуты, CDATA, комментарии, PI, исходные фрагменты; UTF-8, UTF-16LE/BE, Windows-1251; сохранение BOM и переводов строк. Проверка побайтного чтения/записи, некорректного XML и ошибок кодирования. Это первый реализуемый этап.

### 2. Правила и сопоставление

XML-схема базы, один профиль на root, транзитивное наследование, составные ключи, автоопределение и проверка уникальности. Атомарное сохранение, блокировка параллельной записи, резервная копия. Объяснение примененного правила. Проверка на реальных тройках XML 1С.

### 3. Движок и CLI driver

Трехстороннее слияние, независимые правки, удаления, добавления, порядок, перемещения, изменение идентификаторов. При конфликте %A побайтно неизменен. Проверки в временных Git-репозиториях, в том числе имена с пробелами и кириллицей.

### 4. Отдельное интерактивное приложение и Git merge tool

Начать интерфейсную работу с подготовки и редактора недостающих правил. Мастер показывает доступные атрибуты/элементы, значения ключей, дубликаты и источник наследования. Сравнение разрешается только после устранения пробелов в настройках. Затем добавить три DOM с синхронной навигацией и загрузкой ветвей по требованию, выбор изменений на уровне узла/атрибута/текста, ручное соответствие, пересчет и отмену действий. Отдельный EXE с собственным окном и локальным портом; запуск и ожидание из CLI. Проверить, что закрытие окна останавливает сервер, освобождает порт и сообщает отмену Git. Проверить параллельные запуски в разных RDS-сессиях и несколько операций одного пользователя. Сохранение результата и корректный статус для Git.

### 5. Производительность и выпуск

Корпус больших XML 1С; измерение времени разбора, сопоставления, слияния, записи и пиковой памяти. Индексы ключей и пакетная сборка детей. Бенчмарки узких/широких деревьев, перестановок и большого CDATA. Установщик/команда настройки Git, документация, сборка Windows.

Численные пределы времени и памяти устанавливаются после получения репрезентативного корпуса пользователя, а не по искусственно выбранному размеру.

## Проверка качества

- `merge(B, B, R)` семантически равно R, `merge(B, L, B)` равно L, `merge(B, L, L)` равно L при соблюдении политики оформления local.
- Перестановки в неупорядоченной коллекции не создают содержательных конфликтов.
- Дубликаты ключей не сопоставляются произвольно.
- Имена namespaces сравниваются по URI, а не префиксу. Необъявленные префиксы и неоднозначные атрибуты отклоняются.
- Кодировка, BOM, CRLF/LF/CR и CDATA проверяются побайтно.
- Ошибки разбора, конфликты, отмена и невозможность кодирования не изменяют файл результата.
- Обновление базы правил не теряет изменения параллельного процесса.

## Библиотеки и решение первого этапа

Рассмотрены beevik/etree (удобный изменяемый DOM), antchfx/xmlquery (XPath/дерево), lestrrat-go/libxml2 (нативная зависимость). Обычная сериализация DOM не дает достаточного контракта на сохранение исходного представления.

Первый прототип использует стандартный `encoding/xml` для проверки XML и чтения токенов, собственный тонкий DOM с диапазонами исходного текста и `golang.org/x/text` для кодировок. Это позволяет отдельно хранить семантические значения и исходные данные. Решение пересматривается по результатам тестов и измерений, а не по предположению о скорости библиотек.

Источники: https://pkg.go.dev/github.com/beevik/etree, https://pkg.go.dev/github.com/antchfx/xmlquery, https://github.com/lestrrat-go/libxml2, https://pkg.go.dev/encoding/xml, https://git-scm.com/docs/gitattributes.


## Уточнение общей настройки и каталога ERP

Для каждого профиля root используется пункт «Все элементы» (`selector="*"`). Приоритет: собственное правило тега, затем общая настройка профиля. Наследование от родителя применяется только для совместимости в старых профилях без общей настройки. `order="default"` сохраняет живую ссылку на общий порядок, включая перенесенные `UseDefault` из `.pmfmt`.

Каталог `known-element` содержит обнаруженные имена/URI тегов, атрибутов и дочерних элементов. Наличие записи в каталоге не создает индивидуального ключа и не отменяет общую настройку. Сканирование ERP выполняется потоково в нескольких процессах, без изменения исходных файлов; результат и пропущенные документы можно записать в локальный отчёт, который не публикуется.
