# Выпуск версий

Выпуск запускается при отправке в GitHub и GitVerse тега вида `vМАЖОР.МИНОР.ПАТЧ`, например `v0.3.0`. Тег должен указывать на проверенный коммит с файлами `.github/workflows/release.yml` и `.gitverse/workflows/release.yml`. Сначала отправьте коммит в `main` обоих репозиториев, затем создайте и отправьте один и тот же тег:

```sh
git push origin main
git push gitverse main
git tag -a v0.3.0 -m "XML Merge v0.3.0"
git push origin v0.3.0
git push gitverse v0.3.0
```

GitHub Actions проверяет точный формат тега и выполняет тесты на Windows и Linux. После успешной сборки обоих комплектов он публикует [GitHub Release](https://github.com/alexey-marochkin/xml-merge-driver/releases). GitVerse CI выполняет тесты на Linux, собирает Linux-комплект и кросс-компилирует Windows-комплект на облачном Linux-раннере, затем публикует GitVerse Release. Оба релиза содержат `XmlMerge-Windows-x64-<версия>.zip`, `XmlMerge-Linux-x64-<версия>.tar.gz` и контрольные суммы `SHA256SUMS.txt`. Windows-комплект содержит собственное окно WebView2; Linux-комплект открывает тот же интерфейс в браузере. Оба содержат готовые `rules.xml` и `merge-policy.xml`.

Для GitVerse нужен персональный токен с правом «Репозитории → Запись». Сохраните его в настройках GitVerse-репозитория как секрет `RELEASE_API_KEY`; значение не должно попадать в Git, URL удалённого репозитория или консольный вывод. Для локальной отправки коммитов и тегов настройте Git Credential Manager с отдельным токеном или SSH-ключ. Удалённый репозиторий должен называться `gitverse` (его URL доступен на странице репозитория GitVerse). Секрет нужен только GitVerse CI для публикации файлов релиза.

Если тест или сборка на одной площадке не прошли, её релиз не публикуется. Проверьте состояние обоих CI/CD запусков; если ошибка в исходном коде, исправьте её в новом коммите и создайте **новый** тег версии. Не переносите опубликованные теги на другие коммиты. Старые теги, перенесённые при импорте репозитория, не запускают выпуск повторно.
