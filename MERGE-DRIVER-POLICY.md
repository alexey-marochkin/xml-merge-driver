# Git merge driver: правила старого скрипта и новая реализация

## Что исследовано

Исходный файл: `scripts/mergexml.py`. Исходный Oso-скрипт сохранён только локально и не публикуется.

Пример команды исходного скрипта в пользовательском Git config:

```text
python C:/Tools/XmlMerge/scripts/mergexml.py --local %A --remote %B --base %O --result %P -b %S -l %X -r %Y
```

В старой установке путь к скрипту содержал пробелы, но не был заключён в кавычки. В новой настройке это исправлено.

## Поведение исходного Python-скрипта

1. `%A`, `%B`, `%O` — временные файлы local, remote, base. Параметр `--result %P`, несмотря на название, используется как **исходный путь в репозитории**, а не как место записи. Результат всегда записывается в `%A`.
2. `%S`, `%X`, `%Y` разбиваются по первому двоеточию. Первые части считаются ревизиями. Base и local нужны только для печати диагностических сообщений. Для remote выполняется поиск коммита в Git.
3. Репозиторий открывается в текущей рабочей папке. Имя текущей ветки берётся из HEAD.
4. Для remote проверяется локальная ветка `origin1c`: она должна указывать на remote-коммит **либо содержать его среди предков**. Одного совпадения имени remote-ветки не требуется. Если метка содержит `Temporary merge branch`, эта проверка пропускается.
5. Файл допускается к выбору версии целиком при выполнении хотя бы одного условия:
   - его basename точно равен `Rights.xml`, `Form.xml`, `Template.xml`, `Schedule.xml` или `ru.html`;
   - сравнение **local с remote, без base** через `xmldiff` вернуло ровно одно изменение атрибута `version`;
   - сравнение вернуло ровно два изменения: сначала `version`, затем `uuid`.
6. Для допущенного файла действует приоритет:
   - текущая ветка — `origin1c`: оставить local и вернуть успех;
   - иначе remote принадлежит истории `origin1c` **или** исходный путь содержит `РТ_` **или** исходный путь содержит `html`: скопировать remote целиком в local и вернуть успех;
   - иначе перейти к обычному слиянию.
7. Обычное слияние запускает `C:/Program Files/Oso/XMLMerge/2/OsoXMLMerge.exe` с `-merge -silent -checkconflicts`, передавая все три файла и local как результат.
8. Скрипт возвращает конфликт только при отрицательном коде Oso. Любой положительный код ошибочно трактуется как успех независимо от его значения.

Все сравнения имён и подстрок чувствительны к регистру. Проверка `html` относится ко **всему пути**, а не только расширению. Условия пути применяются только после допуска файла из пункта 5. Текущая `origin1c` имеет приоритет над всеми условиями выбора remote. Список файлов не означает безусловное исключение из слияния.

Семантика принадлежности коммита ветке подтверждена в [реализации pygit2 Branches._valid](https://raw.githubusercontent.com/libgit2/pygit2/master/pygit2/branches.py). Параметры драйвера описаны в [Git gitattributes](https://git-scm.com/docs/gitattributes).

## Выбранная реализация

Команда `xmlmerge.exe git-driver` реализована на Go. Обычный `xmlmerge.exe merge` остаётся универсальным XML-слиянием без правил выбора поставщика.

Драйвер работает внутри одного EXE: не запускает Python, `xmldiff`, `pygit2`, Oso или второй процесс XML Merge. При одинаковых local/remote сразу возвращает успех. Для файлов из списка не вычисляет XML-различия. Проверяет Git только для файлов, к которым применим выбор версии целиком. После решения не запускает дополнительные проверки, которые уже не могут изменить результат.

Сравнение допустимых изменений имеет линейную сложность по размеру XML: используются наш парсер, обход соответствующих узлов и проверка физического результата. Поиск похожих узлов и построение списка операций `xmldiff` не выполняются. DOM для этой проверки временные и не изменяют исходные файлы. При необходимости обычного слияния вызывается существующий Go-движок в том же процессе. Ветку и её историю проверяет установленный Git, без shell-интерпретации аргументов.

Выбор Go основан на устранении запуска интерпретатора, импорта библиотек и внешнего XML-движка. Численного сравнения с исходным скриптом нет: у обнаруженного `python` отсутствуют `xmldiff` и `pygit2`. Контрольный замер первоначального Go-проверяющего алгоритма на 1000 элементах (около 78 КБ суммарно в двух документах) дал примерно 4,34 мс за проверку; это не время полного Git merge. Воспроизводимый микротест: `go test ./internal/gitdriver -run '^$' -bench BenchmarkVersionOnly -benchmem`.

## Настройка через --policy

Рабочий файл — `bin/merge-policy.xml`; начальный образец — `merge-policy.xml` в корне проекта. Обычная сборка копирует образец в `bin` только при отсутствии рабочего файла, поэтому ручные изменения не перезаписываются.

```xml
<merge-policy version="1">
  <supplier>
    <branch>origin1c</branch>
  </supplier>
  <eligible-files>
    <file>Rights.xml</file>
    <file>Form.xml</file>
    <file>Template.xml</file>
    <file>Schedule.xml</file>
    <file>ru.html</file>
  </eligible-files>
  <eligible-changes>
    <change><attribute name="version" /></change>
    <change>
      <attribute name="version" />
      <attribute name="uuid" />
    </change>
  </eligible-changes>
</merge-policy>
```

| Поле | Значение |
| --- | --- |
| `supplier/branch` | Список точных имён локальных веток поставщика, без `refs/heads/`. Например, отдельные записи `origin1c` и `vendor/releases`. Маски не используются. |
| `eligible-files/file` | Точные имена файлов без каталогов; маски не используются. |
| `eligible-changes/change` | Одна допустимая комбинация изменений. Несколько комбинаций соединены условием «или». |
| `change/attribute/@name` | Имя атрибута без namespace. В документе должно измениться ровно одно значение каждого указанного атрибута и больше ничего. Узел может находиться на любой глубине. |
| `prefer-remote-paths/contains` | Совместимость со старой политикой: безусловный выбор remote у допущенного файла по подстроке пути. В рабочем файле эта группа отключена, поскольку обходит определение стороны поставщика. |

Удаление записи отключает соответствующее условие; отсутствие обеих групп допуска отключает выбор поставщика целиком. В `supplier` должна быть хотя бы одна запись `branch`; пустые имена и дубликаты запрещены. Прежняя запись `<supplier branch="origin1c" />` также поддерживается. Если текущая ветка входит в список, выбирается local; иначе проверяется имя remote-ветки, а для SHA — основная цепочка поставщика, как описано ниже. Если обе стороны относятся к поставщику, сохраняется прежний приоритет local. Пустая подстрока пути запрещена. Файл политики перечитывается при каждом вызове. Ошибка или отсутствие файла политики не маскируются успехом.

`--policy` управляет **выбором версии файла целиком**. `--rules` управляет **идентификацией узлов и порядком детей при структурном слиянии**. `settings.xml` содержит только предпочтения интерфейса. Для политики пока используется редактирование XML, отдельного экрана нет.

Без `--policy` команда `git-driver` ищет `merge-policy.xml` рядом с EXE. Явные относительные `--policy` и `--rules` разрешаются относительно текущей рабочей папки. В пользовательском Git config задаются абсолютные пути, чтобы драйвер одинаково работал из разных репозиториев.

## Согласованные правила определения стороны поставщика

Правила предназначены для обычного двухстороннего `git merge`. Выгрузки поставщика последовательно коммитятся непосредственно в ветки из `supplier/branch`. Можно сливать любой старый коммит выгрузки, а не только вершину ветки.

1. Для допущенного к выбору целиком файла текущая ветка из списка поставщиков означает поставщика на стороне **local**. Если обе стороны относятся к поставщику, сохраняется приоритет local.
2. Если метка remote указывает на конкретную локальную ветку, её полная ссылка сравнивается со списком. Ветка поставщика означает **remote**. Явно указанная рабочая ветка не становится поставщиком из-за общей истории или совпадения вершины. Ссылки `refs/remotes/...` не приравниваются к локальным веткам по суффиксу имени.
3. Если передан SHA, тег или выражение ревизии, не обозначающее конкретную ветку, коммит проверяется в цепочке **первых родителей** (`git rev-list --first-parent`) любой существующей ветки поставщика. Несуществующие в данном репозитории записи списка пропускаются. Сравнение ссылок и имён точное, с учётом регистра.
4. Найденный старый коммит означает поставщика на стороне **remote**. Используется содержимое переданного Git файла remote от этого коммита; более поздние выгрузки не подставляются.
5. Коммиты боковой рабочей ветки, влитой обычным merge в поставщика, не попадают в его основную цепочку. Сам merge-коммит и последующие выгрузки в основной цепочке считаются состояниями ветки поставщика.
6. Если роль не установлена, вызывается обычное трёхстороннее XML-слияние. Неизвестная метка не даёт права выбрать remote целиком. Ошибки чтения истории возвращают ошибку без изменения local.

Например: `origin1c: A → B → C → D`, рабочая ветка сливает SHA `B`. Поставщик — remote от `B`, даже если `D` намного новее. Если рабочая ветка с именем `working` указывает на тот же `B`, явно заданное `git merge working` не включает приоритет поставщика.

Список защищённых файлов и допустимых комбинаций изменений по-прежнему определяет, **к каким файлам** применяется выбор версии целиком; сторона поставщика определяет, **откуда** брать файл. При выборе файла целиком переносится и его значение `version`. Отдельная политика целевой версии при содержательном объединении XML пока не добавлена.

Старые условия `РТ_` и `html` удалены из начального и рабочего XML-файлов политики. Префикс `РТ_` обозначает наши объекты и не является основанием выбирать remote. Новое безусловное правило выбора рабочей стороны для этого префикса не добавлено: между рабочими ветками он не определяет победителя.

Ограничения: это соглашение о структуре истории, а не сохранённый Git признак происхождения коммита. Общие начальные коммиты и рабочие изменения, оказавшиеся в основной цепочке через fast-forward или прямой коммит, неотличимы от других её состояний. Для rebase, cherry-pick и detached HEAD нужна отдельная передача/проверка контекста; надёжность определения стороны для этих операций не заявляется.

## Осознанные отличия и исправления

- Порядок перечисления атрибутов в комбинации не влияет на её смысл. `uuid + version` и `version + uuid` теперь эквивалентны.
- Допуск по изменениям консервативен: перестановки узлов/атрибутов, изменение пробелов, переводов строк, CDATA, комментариев, префиксов или кодировки не считаются «изменением только версии». Тогда вызывается обычное структурное слияние, которое использует `rules.xml`. Это предотвращает выбор файла целиком по неточному сопоставлению `xmldiff`.
- Если правило выбрало remote целиком, он копируется побайтно, включая его кодировку и переносы строк. Это сохранённая семантика старого скрипта. При обычном структурном слиянии действуют ограничения движка на сохранение кодировки local.
- Неразрешимая remote-метка не считается доказательством принадлежности поставщику; выполняется обычное слияние. Ошибка запуска Git или проверки истории возвращает ошибку.
- Коды возврата: `0` — успешный результат; `1` — конфликт; `2` — ошибка запуска, входных данных или настроек. Конфликт/ошибка не меняют `%A`. `%P` никогда не используется как путь записи.
- Установлено `merge.xmlmerge.recursive=binary`: правила поставщика не применяются к внутренним виртуальным предкам при сложном Git merge.
- Python-файл сохранён как тонкий совместимый запускатель нового EXE со стандартной библиотекой. Он принимает прежние `--result`, `-r`, `-b`, `-l`; старые зависимости не нужны. Git вызывает Go напрямую.

## Вывод в консоль

Команда `git-driver` по умолчанию пишет в stderr одну итоговую строку на обработанный файл: исходный путь, результат и основание решения. Например:

```text
[xmlmerge] "Forms/Form.xml": выбрана remote — коммит поставщика в основной цепочке "refs/heads/origin1c"; файл из защищённого списка
[xmlmerge] "data.xml": XML-слияние выполнено — политика выбора файла целиком неприменима
[xmlmerge] "data.xml": конфликт; local не изменён — политика выбора файла целиком неприменима
```

Ошибки и подробности конфликтов дополнительно выводятся существующим движком. Итоговая строка об успешной записи появляется только после её завершения. Ошибка загрузки настроек или чтения файлов также сопровождается строкой с исходным путём, если параметры уже разобраны.

Параметр `--verbose` добавляет пути настроек, remote-метку и разрешённый коммит, текущую ветку, основание выбора файла целиком (включая имена атрибутов), проверенные цепочки первых родителей, найденную ветку поставщика, запуск обычного XML-слияния, итоговый код и время выполнения. Если Git-проверка не нужна (совпадающие файлы или неприменимая политика), это явно сообщается; дополнительные обращения к Git ради имени текущей ветки не выполняются. При нескольких ветках подробный режим может выполнить дополнительные проверки, чтобы назвать ветку, в которой найден коммит; решение от режима журнала не зависит.

Журнал политики не выводит содержимое XML или значения его атрибутов. Все его строки содержат путь файла; переводы строк и управляющие символы в путях/метках экранируются. Сохраняется существующая диагностика конфликтов с путями XML-узлов. В GUI Git вывод доступен там, где программа показывает stderr внешнего драйвера.

В пользовательской команде Git краткий вывод включён автоматически новой сборкой. Для подробного режима добавьте `--verbose` к команде `merge.xmlmerge.driver`. Политика XML и коды возврата от уровня подробности не меняются.

## Команда Git

Значение `merge.xmlmerge.driver`:

```text
"C:/Tools/XmlMerge/bin/xmlmerge.exe" git-driver --base "%O" --local "%A" --remote "%B" --path %P --remote-label %Y --rules "C:/Tools/XmlMerge/bin/rules.xml" --policy "C:/Tools/XmlMerge/bin/merge-policy.xml"
```

`%P` и `%Y` специально оставлены без дополнительных кавычек: Git уже экранирует их для shell. Повторное оборачивание ломает пути/метки с пробелами и апострофами. Это проверено по [коду Git merge-ll.c](https://raw.githubusercontent.com/git/git/master/merge-ll.c) и реальным пробным слиянием.

Существующие `.gitattributes` продолжают использовать имя `xmlmerge`. Настройки Araxis как интерактивного mergetool этим изменением не затрагиваются.

## Проверки и восстановление

- `go test ./...` — разбор политики, настройка нестандартной ветки/атрибутов/путей, выбор local/remote, старые SHA и теги, рабочие ветки на общей вершине, исключение боковых рабочих коммитов после обратного слияния, несколько и отсутствующие ветки поставщика, неизвестные метки, сохранность кодировок и переносов строк.
- `scripts/check-supplier-driver.ps1` — настоящий Git merge во временном репозитории: remote задан SHA старой выгрузки в основной цепочке `origin1c`, пути содержат кириллицу/пробелы/апостроф, независимые изменения сливаются, конфликт оставляет local неизменным и три стадии в индексе.
- `scripts/check-supplier-driver.ps1 -UseGlobal` — та же проверка с пользовательским драйвером.

Установщик сохраняет предыдущее значение `merge.xmlmerge.driver` в `git-driver.previous.txt` рядом с EXE. Для отката можно вернуть эту команду через `git config --global merge.xmlmerge.driver`, затем при необходимости удалить добавленное значение `merge.xmlmerge.recursive`.

## Служебные файлы

`keep-local-files/file` задаёт точное имя файла, который сохраняется со стороны local до проверки правил выбора поставщика. Для последовательных обновлений ERP local — наша ветка ERP_*. В список включён `ConfigDumpInfo.xml` по указанию пользователя.

TXT-файлы не подключаются к XML-драйверу автоматически и не входят в `eligible-files`. При ручном решении конфликтов XML определяется по содержимому: для XML внутри `.txt` драйвер запускается вручную; прочие TXT разбираются в своём формате. Предпочтение поставщика для `Template.txt` применяется вручную. Для политики сохранения ConfigDumpInfo действует `Config/ConfigDumpInfo.xml merge=osoxmlmerge`, переопределяющий прежний binary merge.
