# XML Merge

**Для сотрудников:** [установка, настройка Git и Git Extensions, размещение готовых файлов](INSTALL-RU.md).

Структурное трехстороннее слияние XML на Go для Windows и Linux. В Windows редактор работает в окне WebView2, в Linux — в локальном браузере. [Установка для Windows](INSTALL-RU.md), [установка для Linux](INSTALL-LINUX.md), [выпуск версий](RELEASING.md). Согласованные требования и этапы находятся в [SPECIFICATION.md](SPECIFICATION.md).

## Текущее состояние

Реализован консольный прототип и отдельное интерактивное приложение:

- DOM с исходными фрагментами XML, порядком атрибутов, CDATA и переводами строк.
- UTF-8, UTF-16LE/BE и Windows-1251; сохранение BOM, отказ при непредставимых символах.
- XML-база профилей пользователя, наследование и три способа получения ключа.
- Автоматическое выявление простых ключей и сохранение правил с пометкой происхождения.
- Слияние независимых атрибутов и дочерних элементов, добавления и удаления, обработка порядка.
- CLI merge driver: запись только после успешного слияния, проверки XML и кодировки; при конфликте local не изменяется.
- Атомарная запись, блокировка обновления базы правил и резервная копия.
- CLI запускает `xmlmerge-ui.exe`, передает пути отдельными аргументами и ожидает код завершения.
- Собственное окно Windows на WebView2. Каждый экземпляр автоматически получает свободный локальный порт; настраивать его не требуется.
- Подготовка правил до сравнения, редактор трех типов ключа, составные ключи, проверка дубликатов и отсутствующих значений, примеры из трех XML.
- Сравнение недоступно, пока правил недостаточно. После подготовки доступны три сопоставленных DOM с раскрытием ветвей по запросу.
- Явное сохранение результата, отмена без изменения XML, остановка сервера при закрытии окна. Закрытие не ожидает завершения долгого вычисления; начатая атомарная запись имеет отдельную синхронизацию.
- Дополнительная личная база через `--user-rules`; правила из `--rules` имеют приоритет на совпадающих путях. Проверка версии настроек перед сохранением.

Это еще не целевая первая версия. При конфликте UI пока позволяет явно принять весь local или весь remote; выбор отдельных изменений и ручное соответствие остаются следующим этапом. Полноценные перемещения между родителями и оптимизация больших файлов также предстоят. Неоднозначные ключи и обнаруженные перемещения между родителями дают конфликт. Комментарии и mixed content пока сливаются как цельный блок содержимого; изменения namespaces и оболочки документа обрабатываются консервативно. DTD и иные кодировки пока отклоняются. До проверки на реальном корпусе 1С прототип не следует считать проверенным для производственных слияний.

Корень и единственные дочерние элементы одного имени имеют встроенное однозначное структурное правило. Пользовательский ключ нужен для повторяющихся групп. Проверяются все группы, в том числе в добавленных ветвях и у разных экземпляров родителей; неподходящее явное правило не заменяется молча автоматически.

## Сборка и проверки

Требуется Go 1.26.3 или новее и Git for Windows для интеграционной проверки. Для запуска UI нужен Microsoft Edge WebView2 Runtime. CLI запускается и без него; CGo для сборки этих приложений не нужен.

```powershell
go test ./...
go vet ./...
pwsh -File scripts/build.ps1
pwsh -File scripts/check-git.ps1
```

Если среда ограничивает запись в общий кеш Go:

```powershell
$env:GOCACHE = Join-Path (Get-Location) '.cache\go-build'
```

Интеграционная проверка создает отдельный временный репозиторий и сообщает его путь. Настройки пользовательских репозиториев не меняются.

## Команды

```powershell
.\bin\xmlmerge.exe inspect examples\base.xml
.\bin\xmlmerge.exe roundtrip examples\base.xml bin\copy.xml
.\bin\xmlmerge.exe rules validate examples\rules.xml
Copy-Item examples\local.xml bin\result.xml
.\bin\xmlmerge.exe merge --base examples\base.xml --local bin\result.xml --remote examples\remote.xml --rules examples\rules.xml
```

`merge` записывает результат только при успехе: в `--output`, если он указан, иначе в `--local`. Код возврата: 0 — успех, 1 — конфликт, 2 — ошибка входа/настроек/записи. Для Git оба ненулевых кода означают неуспешное слияние. Часть технической диагностики движка пока на английском.

При необходимости отдельный путь результата задается через `--output`. Автоматический режим не открывает окно.

## Интерактивный запуск

Редактор базы правил работает и без сравниваемых XML:

```powershell
.\bin\xmlmerge-ui.exe
.\bin\xmlmerge-ui.exe --rules "D:\Settings\xmlmerge-rules.xml"
```

Без параметров открывается `rules.xml` рядом с `xmlmerge-ui.exe`, независимо от текущей рабочей папки. Если файла нет, приложение создает пустую XML-базу. С `--rules` открывается указанный файл (отсутствующий также создается). Существующий файл при открытии не перезаписывается; ошибка чтения или некорректный XML показываются пользователю. Для создания и сохранения нужны права записи в выбранную папку.

В отдельном редакторе можно создавать профили, добавлять, изменять и удалять правила, выбирать поля составного ключа и порядок детей. Без исходных документов имена полей и пути вводятся вручную; уникальность ключей проверяется при последующей подготовке XML к сравнению. В отдельном редакторе правки накапливаются в памяти при переходах между правилами и профилями. Общая кнопка с дискетой рядом с путём файла или Ctrl+S сохраняет весь файл, включая текущее редактируемое правило. Значок обновления перечитывает файл с диска; статус под путём показывает наличие несохранённых изменений. Перед закрытием (в том числе крестиком окна) или обновлением можно сохранить, отбросить изменения либо отменить действие. Сохранение защищено от перезаписи изменений другого экземпляра приложения; предыдущая версия остается в `.bak`. Обычное закрытие отдельного редактора возвращает 0.

Для трехстороннего сравнения:

```powershell
.\bin\xmlmerge.exe compare --rules examples\rules.xml --base examples\base.xml --local examples\local.xml --remote examples\remote.xml --output bin\result.xml
```

Тот же запуск напрямую:

```powershell
.\bin\xmlmerge-ui.exe compare --rules examples\rules.xml --base examples\base.xml --local examples\local.xml --remote examples\remote.xml --output bin\result.xml
```

Варианты: `xmlmerge ui rules` — редактор правил на трех документах; `xmlmerge mergetool` — интерактивное разрешение конфликта; `xmlmerge merge --interactive` — явный запуск окна из команды merge. Для compare/mergetool параметр `--output` обязателен; он может совпадать с `--local`, но не с base, remote или настройками. `merge --interactive` по умолчанию использует local как output. Оба EXE размещаются в одной папке.

UI в режиме слияния возвращает 0 только после сохранения результата, 3 при отмене/закрытии и 2 при ошибке. Правила сохраняются отдельной кнопкой: последующая отмена слияния не отменяет уже сохраненные настройки. Если файл результата изменился внешним процессом после запуска, сохранение отклоняется.

Демонстрация недостающего правила с отдельными тестовыми файлами:

```powershell
pwsh -File scripts/demo.ps1
```

Выберите три атрибута `language`, `section`, `variant`, нажмите «Проверить правило», затем «Сохранить и применить». Только после этого станет доступно сравнение. Демонстрация создает отдельную папку `.cache/demo-*` и не использует личную базу правил.

Для настройки корня, просмотра автоматически созданных и унаследованных правил отключите фильтр «Только требующие настройки». Настройка корня позволяет менять значимость порядка его детей.

Опциональный `--user-rules PATH` добавляет личную базу. Автоматически найденные правила тогда сохраняются в нее; ручная кнопка сохраняет в основной `--rules` (путь показан в редакторе). Это явное редактирование командного файла; публикация выполняется обычным коммитом. Переключатель явного личного переопределения командных правил пока не реализован.

Путь базы по умолчанию для слияния: `%LOCALAPPDATA%\XmlMerge\rules.xml`; для отдельного редактора без документов — `rules.xml` рядом с приложением. Для тестов используйте `--rules`, чтобы не менять рабочую базу. Файл `.lock` удерживается на время чтения/обновления/записи. Если процесс был аварийно завершен, перед ручным удалением оставшегося `.lock` убедитесь, что других процессов приложения нет.

## Внешний вид

Кнопка с луной или солнцем в правом верхнем углу переключает светлую и тёмную темы; подсказка при наведении показывает действие. Светлая тема использует приглушённый фон и контрастные границы. Левую панель можно расширять перетаскиванием вертикального разделителя. Когда разделитель выбран клавишей Tab, стрелки ← → меняют ширину, Shift ускоряет изменение; двойной щелчок возвращает исходную ширину.

Тема и ширина панели автоматически сохраняются в `%LOCALAPPDATA%\XmlMerge\settings.xml` и восстанавливаются при следующих запусках. Файл создаётся при первом запуске интерфейса; первая настройка — `<theme>light</theme>` или `<theme>dark</theme>`, следующая — `<sidebar-width>` в пикселях. Настройки общие для окон одного пользователя Windows и хранятся отдельно от правил XML. Вспомогательный preview использует `settings.xml` рядом со своей тестовой базой правил.

## Правила

Основная настройка — **корень документа + имя элемента на любой глубине**. Полный путь не требуется. Формат версии 2 использует `selector="Item"`; `selector="*"` задает настройку по умолчанию. Для независимости от префиксов применяется расширенное имя, например `selector="{urn:example}Item"`. Новые правила из сравнения и автоматически найденные ключи используют расширенные имена и проверяются во всех вхождениях этого имени. Старые правила версии 1 с `path` поддерживаются как точечные исключения.

Рабочая база [rules.xml](rules.xml) содержит 22 профиля, 61 правило и каталог 2 140 элементов. Она дополнена по выгрузке ERP; копия в `bin/rules.xml` открывается при запуске редактора без параметров. База создана с использованием выгрузки XML и импортера форматов `.pmfmt`. Конвертер — `scripts/import-pmfmt.py` (Python 3, стандартная библиотека); исходные `.pmfmt` в репозиторий не входят.

Исходные спецификации не содержат URI пространств имен: импортированные профили используют явный `namespace="*"`, а имена с префиксами и поля с `lexical="true"` сохраняют исходное написание. При смене префикса может понадобиться настройка по URI. Идентичность самого XML-узла по-прежнему включает URI. Короткие контексты вроде `field/field` сохраняют вложенные настройки исходного формата и также применяются на любой глубине.

Пункт **«Все элементы»** (`selector="*"`) — общая настройка root: собственное правило тега имеет приоритет, иначе применяется именно она. `order="default"` у собственного правила сохраняет ссылку на общий порядок, а не копию значения. Это соответствует `UseDefault` в исходных `.pmfmt`. Наследование от предка сохранено только для старых профилей без `*`; `no-inherit` используется для совместимости. `trim-space="true"` обрезает краевые XML-пробелы только при вычислении ключа, не меняя текст документа. `mode="auto"` у `*` означает отсутствие исходного ключа: он подбирается при подготовке XML. Политика исходного табличного документа `comments="ResolveRight"` не перенесена — конфликт комментариев требует решения.

Пример — [examples/rules.xml](examples/rules.xml). Путь содержит расширенные имена: `/{}Root/{}Item` для пустого namespace, `/{urn:example}Root/{urn:example}Item` для заданного URI. Имена префиксов не участвуют в идентичности.

`mode` принимает `attribute`, `element`, `text`. Поля задаются элементами `field` с атрибутами `name` и необязательным `namespace`. Несколько полей составляют ключ. `order` определяет порядок детей этого узла: `significant` или `insignificant`. При отсутствии собственной настройки действует правило «Все элементы» профиля; для старых профилей без него сохраняется наследование предка. Для смешанного содержимого правило `text` неприменимо.

Автоматические правила сохраняются и при конфликте данных, если сами были однозначно выведены. Пользовательские настройки не перезаписываются. При конкурентном изменении базы сохраняются только отсутствующие пути; текущий запуск использует свой первоначальный снимок правил.

## Git driver

Для перенесённой логики поставщика из `mergexml.py` используется команда **`xmlmerge git-driver --policy ...`**. Она уже подключена в пользовательском Git config и читает `bin/merge-policy.xml` и `bin/rules.xml`. Ветка поставщика, имена файлов, комбинации изменённых атрибутов и подстроки пути задаются в политике. Исследование старого скрипта, точные приоритеты, отличия, команда подключения и восстановление описаны в [MERGE-DRIVER-POLICY.md](MERGE-DRIVER-POLICY.md). `scripts/mergexml.py` оставлен как совместимый запускатель нового EXE; исходный Oso-скрипт не публикуется.

Ниже приведена настройка универсальной команды `merge`, которая выполняет структурное слияние без особого выбора поставщика.

Пример `.gitattributes`:

```gitattributes
*.xml merge=xmlmerge
```

Пример секции `.git/config`, после размещения бинарника в постоянном месте:

```ini
[merge "xmlmerge"]
    name = XML structural merge
    driver = \"C:/Tools/XmlMerge/xmlmerge.exe\" merge --base \"%O\" --local \"%A\" --remote \"%B\"
    recursive = binary
```

Настройка `recursive = binary` исключает обучение правил на внутренних промежуточных слияниях предков.

Дополнительно для Git merge tool (замените путь к EXE и базе правил):

```ini
[mergetool "xmlmerge"]
    cmd = \"C:/Tools/XmlMerge/xmlmerge.exe\" mergetool --rules \"C:/Settings/xmlmerge-rules.xml\" --base \"$BASE\" --local \"$LOCAL\" --remote \"$REMOTE\" --output \"$MERGED\"
    trustExitCode = true
[merge]
    tool = xmlmerge
```

Файл командных правил следует исключить из обработки этим драйвером отдельной строкой `.gitattributes`, например `xmlmerge-rules.xml merge=text`.

## Git Extensions: кнопка «Открыть в»

`xmlmerge-select.exe` выбирает редактор по расширению итогового файла: `.xml`
(без учёта регистра) открывается в соседнем `xmlmerge-ui.exe`, остальные файлы —
в Araxis. Он ожидает закрытия редактора и передаёт его код завершения.
Автоматический XML merge driver настраивается отдельно.

Пример локальных настроек репозитория (пути замените на свои):

```ini
[merge]
    guitool = xmlmerge-select
[mergetool "xmlmerge-select"]
    path = C:/Tools/XmlMerge/xmlmerge-select.exe
    cmd = \"C:/Tools/XmlMerge/xmlmerge-select.exe\" --rules \"C:/Tools/XmlMerge/rules.xml\" --araxis \"C:/Program Files/Araxis/Araxis Merge/Compare.exe\" --base \"$BASE\" --local \"$LOCAL\" --remote \"$REMOTE\" --output \"$MERGED\"
    trustExitCode = false
```

В Git Extensions 6.0.5 кнопка «Открыть в» использует `merge.guitool`.
После изменения настроек заново откройте окно разрешения конфликтов.
Выберите файл и нажмите кнопку: XML Merge получает все три исходные версии,
а «Сохранить результат» записывает итог в рабочий файл. Закрытие XML Merge
без сохранения возвращает код отмены 3. Git Extensions проверяет завершение
и изменение файла перед отметкой конфликта решённым.

`trustExitCode = false` сохраняет проверку изменения файла при запуске через
`git mergetool --gui`: успешное завершение Araxis само по себе не доказывает
сохранение результата. Для возврата к глобальному инструменту удалите только
локальный `merge.guitool`: `git config --local --unset merge.guitool`.

## Проверка интерфейса при разработке

`go run ./scripts/preview compare --rules ... --base ... --local ... --remote ... --output ...` запускает те же ресурсы интерфейса для проверки в браузере и выводит локальную ссылку с секретом операции. Это вспомогательный инструмент разработки; в обычном запуске используется собственное окно и секрет не выводится. Preview завершается после сохранения/отмены либо Ctrl+C.

## Каталог элементов из ERP

Рабочая база составлена по большой XML-выгрузке конфигурации 1С: в ней 22 профиля по URI и корневому элементу. Включены также WSDL, XSLT, SVG и XSD. Исходная выгрузка в публичный репозиторий не входит.

`known-element` хранит имя/URI элемента и наблюдавшиеся атрибуты/детей, не создавая отдельного ключа. В редакторе такие теги показываются с пометкой «Используется “Все элементы”». Можно найти тег поиском и создать собственное правило; поля предлагаются из каталога. Собственные ключи проверяются на реальных XML перед сравнением.

Повторный сбор каталога (исходные документы читаются без изменения):

```powershell
python scripts/scan-xml-parallel.py "C:\Data\erp" .cache/erp-inventory.json --workers 4
```

Сканер использует четыре отдельных процесса, ограниченную очередь заданий и потоковый разбор каждого файла. Каталоги `.git`, `.svn`, `node_modules` пропускаются. Текстовые значения не попадают в каталог. Импорт дополняет существующие записи без изменения выбранных ключей; предыдущая база сохраняется в `.before-erp.bak`.

## Иконка приложения

Иконка встроена в оба EXE и используется в окне и шапке интерфейса. Векторный вариант — `assets/xmlmerge.svg`, Windows ICO с размерами 16–256 пикселей — `assets/xmlmerge.ico`. Ресурсы `.syso` для Windows amd64/386/arm64 входят в исходники, поэтому обычная сборка не требует дополнительных инструментов. Для изменения рисунка и пересоздания ресурсов выполните `scripts/build-icon.ps1` (Windows SDK и .NET Framework), затем `scripts/build.ps1`.

Проверки состояния редактора (общее сохранение, ошибки записи, переходы и закрытие): `node --test scripts/test-catalog.cjs`.

`xmlmerge git-driver` выводит итог и причину решения для каждого файла. Параметр `--verbose` включает подробную диагностику определения поставщика, сработавшей политики и времени обработки. Журнал выводится в stderr.

## Решение конфликтов в узлах

Если правил достаточно, приложение автоматически переходит к сравнению.
Во время чтения документов, автоматического слияния и загрузки дерева показаны
анимация ожидания и текущий этап. После подготовки сравнение открывается автоматически.
LOCAL находится слева, BASE → РЕЗУЛЬТАТ по центру, REMOTE справа. Независимые изменения объединяются автоматически;
нерешённые спорные области показывают BASE. При конфликте перемещения между
родителями это только перемещаемые узлы: независимые изменения внутри той же
ветви автоматически остаются в центре и получают метки источника. Подсветка
конфликта не распространяется на остальные изменённые строки ветви.
Сохраняется документ из центра.

Верхняя строка показывает только выбранный конфликт и его номер среди оставшихся
(например, «12 из 300»). «Все конфликты» открывает отдельный список с причинами
и путями; выбор строки переводит к нужному узлу. При открытии сравнения выбран
первый конфликт. Кнопки перехода перебирают все причины, включая несколько
конфликтов одного узла.

Переход к конфликту раскрывает весь путь и показывает конкретный спорный элемент.
Если конфликт затрагивает несколько мест (например, источник и назначение
перемещения), стрелки перехода перебирают эти участки; их номер показан рядом
со счётчиком конфликтов. Весь путь до спорного элемента отмечен красным,
соседние обычные изменения остаются жёлтыми. При прокрутке раскрытые родители
текущей ветви закрепляются сверху компактными строками и сменяются при выходе
из ветви. Редактор текста при этом не открывается. Стрелки → и ← у боковых значений переносят
соответствующий узел целиком в результат, включая добавление или удаление. Несколько
стрелок позволяют собрать поля с обеих сторон. Уже принятые соседние узлы сохраняются.
Стрелка исчезает, когда соответствующая версия совпадает с результатом.

После каждого переноса драйвер пересчитывает конфликты. Решения привязаны
к полному пути с ключами родителей. Решение по одному концу
перемещения не принимает второй конец автоматически: соседняя ветвь сохраняет
прежний результат и свой нерешённый участок до отдельного подтверждения.
Если родитель уже добавлен в результат автоматически, его дочерние элементы
можно переносить стрелками и редактировать текстом, даже когда этот родитель
отсутствует в BASE или LOCAL. Отмена одного решения сохраняет остальные.
Для спорного состава ветви
можно явно подтвердить текущую середину кнопкой «Принять результат узла».
«Отменить решение» отменяет собственное решение выбранного узла; принятый родитель
объединяет решения потомков в одно. Последующие стрелки и правки потомков изменяют
этот родительский результат, сохраняя остальные принятые части.

«Открыть узел» или двойной щелчок открывает только текстовое редактирование. Боковые
тексты доступны для чтения, средний — для правки. Сопоставленные блоки стоят на одной
высоте; пустое место напротив добавления — оформление, которое не попадает в XML.
Жёлтым выделены обычные изменения, красным — конфликтные узлы и блоки текста,
включая ещё не решённые структурные конфликты драйвера. Пустые места напротив
добавлений и удалений сохраняют цвет блока и отмечены штриховкой. При наведении
на стрелку выделяется рамка переносимого блока, его цвет сохраняется.
Кнопки навигации внутри редактора переходят по изменениям и конфликтным блокам текста;
верхняя навигация возвращает к узлам дерева. Стрелки у текстовых блоков заменяют
соответствующую часть центра. Ctrl + клик вставляет исходный блок ниже текущего,
Shift + клик — выше, сохраняя текст центра. Слева стрелки направлены вправо,
справа — влево; модификатор наклоняет их вниз или вверх. Если зажаты обе клавиши,
действует Shift (вставка выше). Пустой исходный блок доступен только для замены
(удаления). Редактируются блоки текста, в том числе многострочные.
«Весь документ» открывает корневой элемент XML. Оба направления прокрутки связаны.
Номера строк, треугольники и кнопки закреплены средствами CSS: горизонтальная
прокрутка двигает текст без запаздывающего пересчёта положения боковых полей.
После переноса редактор сохраняет высоту исходной строки на экране и фокус
в исходной панели. При удалении опорой служит ближайшая строка перед удаляемым
блоком; пересчёт выравнивания не уводит просмотр к другому участку текста.

Текст применяется кнопкой «Применить текст узла» после проверки XML. Ошибка не меняет
принятый результат. Несохранённый текст блокирует сохранение файла; при выходе из
редактора или возврате к правилам приложение предупреждает о его потере.
Файл записывается только кнопкой «Сохранить результат» после решения всех конфликтов.

Проверки выравнивания, переноса блоков и отсутствия добавочных строк:
`node --test scripts/test-line-diff.cjs`.

Жёлтые SVG-треугольники в результате показывают направление переноса изменения:
угол вправо — из LOCAL (слева), влево — из REMOTE (справа), к результату в центре.
Метки показываются и для автоматического слияния. В текстовом режиме треугольники
повторяются на каждой строке принятого блока, включая пустые места при удалении.
При одинаковом изменении обеих сторон показаны оба направления; неизменённый BASE
и текст, не совпадающий ни с одной стороной, не получают предполагаемого источника.
В текстовом редакторе границы переносимых блоков выделены горизонтальными линиями.
Наведение или фокус на стрелке выделяет исходный блок и заменяемую область центра;
подсказка стрелки содержит диапазон строк (либо указывает удаление).
